# Usage API

One read-only call answers "how much, by whom, on what": requests, outcomes, tokens and cost of every app in your organization, over all time or any range. Rows are per period and optionally per one or two dimensions, and `totals` always covers the whole selection.

| Call | Use it for | Scope |
| --- | --- | --- |
| [`GET /usage`](#Read_usage) | Spend, requests and tokens by period, app, model, provider, user, key, source or outcome. | `read` |
| [`GET /apps/{app_name}/keys`](./apps-and-credentials-api#List_gateway_credentials) | Each gateway credential's `usage`: when it was last used and its requests in the last 30 days. | `read` |
| [`GET /users`](./users-api) | Each person's requests and cost for the last 30 days. | `read` |

No extra scope is needed: a key with `read` can call all three. Try them with your own key in the [Management API playground](/llm-gateway-management-playground?tab=usage).

## Build a report

<StepFlow steps={[
  {label: '1. Range', items: ['from / to', 'Omit both for all time']},
  {label: '2. Periods', items: ['granularity', 'total · month · week · day']},
  {label: '3. Breakdown', items: ['group_by (up to 2)', 'app, model, provider, user, key, source, outcome']},
  {label: '4. Narrow', items: ['Filters on any dimension', 'Up to 50 values each']},
  {label: '5. Read', items: ['rows + totals', 'sort, limit, cursor']},
]} />

| Parameter | Values | Default |
| --- | --- | --- |
| `from` | Inclusive start: a date (`YYYY-MM-DD`, UTC midnight) or an RFC 3339 timestamp with a timezone. | The first recorded request |
| `to` | **Exclusive** end: an RFC 3339 timestamp with a timezone, or a date to include that whole UTC day (`to=2026-10-31` ends at `2026-11-01T00:00:00Z`). | Now |
| `granularity` | `total` (one row per group), `month`, `week` (starts Monday) or `day`. All periods are UTC, and `period_start` is the period's first day (`YYYY-MM-DD`). | `total` |
| `group_by` | Up to two of `app`, `model`, `provider`, `user`, `key`, `source`, `outcome`, repeated (`group_by=app&group_by=model`) or comma-separated (`group_by=app,model`). | No breakdown |
| `app`, `model`, `provider`, `user`, `key`, `source`, `outcome` | Filters, comma-separated, at most 50 values each. Apps and emails match case-insensitively. `source` is `gateway`, `sdk` or `copilot_studio`; `outcome` is `served`, `blocked`, `error` or `rate_limited`. | None |
| `sort` | `period` (oldest period first, then highest cost), or `cost`, `requests`, `tokens` (highest first). | `period` |
| `limit`, `cursor` | Rows per page (1 to 5,000) and the previous page's `next_cursor`. Keep the rest of the query unchanged while paging; follow `next_cursor` until it is `null` for a complete export. | `500` |

Filters narrow every number, including `totals`, and `totals` always equals the sum of every row across all pages. Periods without traffic are omitted, so a chart should fill gaps with zero.

## What the numbers mean

| Field | Meaning |
| --- | --- |
| `requests` | Client requests with every outcome. The background cache-refresh requests the gateway sends on its own are not counted. |
| `blocked` | Refused by a policy check before the model call, or blocked by a guardrail. |
| `rate_limited` | Refused by a gateway rate limit, token limit or quota. |
| `errors` | Failed upstream or in the gateway (status 400 or above), excluding blocked and rate-limited requests. A provider's own 429 counts here. |
| `input_tokens`, `output_tokens` | Input includes cached input; `cache_read_tokens` and `cache_write_tokens` break it down. `reasoning_tokens` is part of output where the provider reports it. |
| `cost_usd` | The cost recorded with each request when it ran. It is never re-estimated, and it includes background cache-refresh requests because the provider bills them. |
| `unpriced_requests` | Requests with token usage but no recorded cost, for example a model that had no price when it was called. They add nothing to `cost_usd`. |
| `totals.priced_coverage_pct` | The share of billable requests (those that reached pricing with token usage, background cache-refresh requests included) that have a recorded cost: 100 x (billable - `unpriced_requests`) / billable. Below 100, `cost_usd` understates spend. `null` when nothing was billable. |

- **Dimensions.** `app` uses the app's current name while the app exists, otherwise its recorded name; `app_deleted: true` marks an app that no longer exists. `model` is the served model (after routing and aliases), not the model name the client sent. `key` is a gateway credential id (with `key_name` while the credential exists) and `provider` is the provider label. A value is `null` when it was not recorded, and `user` is `null` when the request carried no identity or data retention removed it.
- **Freshness.** Results can be up to 60 seconds old. `generated_at` is when the data was read, and `data_through` is the effective end of the range (your `to`, or the time of the read). Requests are written a few seconds to minutes after they finish, so the latest ones can be missing.
- **Paging.** A `next_cursor` is tied to the result it came from. If the result is recomputed and has changed (new or late requests), the next page answers `409 collection_changed`: restart without `cursor`. For a stable export, pass a `to` in the past.
- **Cost of a query.** Grouping or filtering by `key` reads more data. Use a bounded range with it. Queries are limited to 20 seconds and 100,000 result rows (`422 result_too_large`).
- **Errors.** An invalid parameter returns `400 invalid_request` with a message such as `to must be after from` or `group_by accepts at most 2 dimensions`. `503 query_timeout` means the query exceeded its time or read limits: narrow it and retry. `503 data_unavailable` means usage data cannot be read right now.

:::tip Need individual requests?
This API returns aggregates. To pull every request log line into your warehouse or SIEM, use the [Log Export API](./log-export-api). To understand one request, use [Explain a request](./monitoring-api#explain-a-request).
:::

## Admin recipes

Each recipe needs a management key with `read`.

```bash
export API="$MANAGEMENT_URL/llmgateway/management/v1"
auth=(-H "Authorization: Bearer $MANAGEMENT_KEY")

# Every row of a usage report, one JSON object per line: follows next_cursor to the
# last page and stops on an error (for example 409 collection_changed: rerun it).
usage_rows() {
  local cursor="" page
  while :; do
    page=$(curl -sG "$API/usage?$1" "${auth[@]}" ${cursor:+--data-urlencode "cursor=$cursor"}) || return 1
    if jq -e '.error' >/dev/null <<<"$page"; then jq -c '.error' <<<"$page" >&2; return 1; fi
    jq -c '.rows[]' <<<"$page"
    cursor=$(jq -r '.next_cursor // empty' <<<"$page")
    [ -n "$cursor" ] || return 0
  done
}
```

The recipes that export a report use `usage_rows`, so they include every page. A recipe that reads one request is labeled "first page".

### Daily spend for the last 30 days

```bash
FROM=$(date -u -d '30 days ago' +%F 2>/dev/null || date -u -v-30d +%F)
usage_rows "from=$FROM&granularity=day" | jq -r '[.period_start, .requests, .cost_usd] | @tsv'
```

### All-time spend by app

```bash
usage_rows "granularity=total&group_by=app&sort=cost" \
  | jq -r '[.app, .requests, .cost_usd, .unpriced_requests] | @tsv'
```

### Top 10 users this month

First page only: `limit=10` with `sort=cost` returns the ten highest-cost users.

```bash
curl -s "$API/usage?from=$(date -u +%Y-%m-01)&granularity=total&group_by=user&sort=cost&limit=10" "${auth[@]}" \
  | jq -r '.rows[] | [.user // "(no identity)", .requests, .cost_usd] | @tsv'
```

### Spend by model per week, for one app

```bash
usage_rows "from=2026-09-01&granularity=week&group_by=model&app=Support%20Bot" \
  | jq -r '[.period_start, .model, .cost_usd] | @tsv'
```

### Find stale keys

Every key in a credentials list or read carries `usage`: `last_used_at` (the most recent request in the last 90 days, or `null` when there was none) and `requests_30d` (requests in the last 30 days, `0` when there were none). List the active keys of an app that nobody used in the last 90 days:

First page only (up to 50 keys); follow `next_cursor` for apps with more.

```bash
curl -s "$API/apps/Support%20Bot/keys" "${auth[@]}" \
  | jq -r '.items[] | select(.status == "active" and .usage != null and .usage.last_used_at == null)
           | [.key_id, .name, .created_at] | @tsv'
```

`usage` itself is `null` only when usage data is unavailable, so the filter skips those keys instead of reporting them as stale. To compare keys across every app over a longer range, group usage by key: `GET /usage?from=2026-01-01&granularity=total&group_by=app,key&sort=requests`. Revoke a stale key with [Revoke a gateway credential](./apps-and-credentials-api#Revoke_a_gateway_credential).

### Error and block rate by app

```bash
usage_rows "from=$FROM&granularity=total&group_by=app,outcome" | jq -r '[.app, .outcome, .requests] | @tsv'
```

For why requests failed at a provider, read [provider health](./monitoring-api#provider-health).
