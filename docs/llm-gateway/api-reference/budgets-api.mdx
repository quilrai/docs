# Budgets API

Manage the same spend, request and token budgets that the Policy Engine's **Budgets & Usage Limits** card configures, from scripts and internal tools. For what a budget counts, how it resets and what happens at the limit, see [Rate, token and budget limits](../cost-and-traffic/rate-token-and-budget-limits#budgets--usage-limits-card).

| Resource | What you can do | Scope |
| --- | --- | --- |
| Budgets | List, read, create, update and delete budgets; apply up to 100 changes as one batch. | `budgets:read`, `budgets:policy` |
| Group budget sets | List and read per-group budget sets, create one, choose whether a person's strongest group or every group applies, add and remove groups, delete it. | `budgets:read`, `budgets:policy` |
| Usage and subjects | Read usage per subject in the current or a past calendar window, a per-budget summary, and every budget that counts a user, app, key or smart group. | `budgets:read` |
| Grants | Give one subject (or every member of a smart group) a temporary limit, then change or revoke it. | `budgets:read`, `budgets:grant` |
| Pricing | Read the effective price of every configured model, set or remove tenant-wide rates, and choose how unpriced models are charged. | `budgets:read`, `budgets:policy` |
| Exemptions | List, add and remove exemptions for users, apps or smart groups. | `budgets:read`, `budgets:policy` |
| Alerts and events | Read and replace alert webhooks, list fired alerts, and poll grant and budget change events. | `budgets:read`, `budgets:policy` |

Try every operation with your own key in the [Management API playground](/llm-gateway-management-playground?tab=budgets).

## Before you start

- **The Policy Engine must be on** for the LLM Gateway. Budgets live in the active policy. With it off, `GET /budgets` returns an empty list with `note: "policy_engine_disabled"`, and writes are refused.
- **Issue a key with budget scopes.** In **Settings > AI Gateway > LLM Gateway > Management API**, pick the scopes below. Budget scopes are independent of `read`: a key with only `budgets:read` can read budgets but not apps.

| Console scope | API scope | Grants |
| --- | --- | --- |
| **Read budgets** | `budgets:read` | Read budgets, usage, subjects, grants, pricing, exemptions, alerts and events. |
| **Manage budget grants** | `budgets:grant` | Issue, change and revoke budget grants. |
| **Configure budgets** | `budgets:policy` | Edit budgets, pricing, exemptions and alert destinations. Each budget, pricing or exemption edit publishes a policy revision. |

`GET /budgets` also returns `caller`, describing what the calling key may do, so a tool can hide actions it cannot perform.

## How writes work

| Write | Effect |
| --- | --- |
| Budget, pricing and exemption edits | Validated like a console publish, then published as **one new policy revision**. Policy text outside the edited budget is kept as is. |
| Batch (`POST /budgets/_batch`) | Up to 100 budget, rate and exemption operations published as one revision, all or nothing. Each op has the same shape as a `POST /controls/_batch` op: `{op, id?, body?, if_match?}`, where `body` is the patch, the new budget, the rate, the exemption or the unpriced-models value. A failure names `op_index`. |
| Grants | Stored outside the policy. Issuing, changing or revoking a grant never publishes a revision. |
| Alert destinations | Replaces the whole webhook list. Stored targets are redacted on read; send the redacted value back to keep a stored URL. |

- **Preview first.** Budget, pricing and exemption writes accept `?dry_run=true` and return the policy diff, diagnostics and the impact on current usage (subjects newly over the limit, newly blocked or unblocked) without publishing. Grant and alert-destination writes do not support `dry_run`.
- **Versions.** Read a budget or grant to get its ETag, then send it quoted in `If-Match`. Budget ETags look like `"r<revision>-<budget_id>"`, so any publish can make them stale (`412`).
- **Creates take an `Idempotency-Key`.** Budget, batch, exemption and grant creation replay the original result for the same key.
- **API-managed vs hand-written.** Budgets created here go into an API-managed policy. Budgets written by hand in the policy editor can have their limit, label, mode, alerts and adjustments changed, but cannot be deleted or re-scoped (`409 budget_not_api_managed`). The same applies to exemptions (`409 exemption_not_api_managed`).
- **Identity fields are fixed.** `id`, `metric`, grouping (`per`) and `window` cannot change (`422 identity_field_immutable`), because usage is tracked against them. Create a new budget instead.
- **Grouping names.** `per` takes the same short names as rate limits (`user`, `app`, `smart_group`, `model`, `provider`, ...) or the full field names (`user.email`, `application.group_key`, ...). Budgets store and return the full names.
- **New exemptions.** `POST /budget-exemptions` returns the new entry as `exemption` and its `exemption_id` in `ids`.
- **Events.** `GET /budget-events` types are past tense: `grant.created`, `grant.updated`, `grant.revoked`, `grant.superseded`, `budget.created`, `budget.updated`, `budget.deleted`, `budget.batch_applied`, `exemption.created`, `exemption.deleted`, `token_rate.updated`, `token_rate.deleted` and `unpriced_models.updated`. Filter with `type`.

## Group budget sets {#group-budget-sets}

A group budget set is one budget per smart group, for example $50 a month for Employees and $500 for Executives. The set decides what happens to someone who is in several of its groups:

| `resolve` | Console option | Effect |
| --- | --- | --- |
| `strongest` | **Their strongest group's budget applies (by rank)** | Only the budget of the person's best-ranked group in the set is checked and charged, with its own limit, counter and grants. The other groups' budgets are skipped. Default for new sets. |
| `strictest` | **Every group's budget applies (strictest wins)** | The person is charged in every group budget they belong to; the first to run out blocks them. |

The best-ranked group is, among the person's groups in the set, the one with the lowest rank number: the `priority` field of the [Smart groups API](./smart-groups-api#rank) (ties by name; disabled groups never count). It is the one with the smallest `rank` (Strength) among them, not necessarily `1`. See [Budgets for several groups](../cost-and-traffic/rate-token-and-budget-limits#budgets-for-several-groups) for the full rules and a diagram.

| Call | Body and effect |
| --- | --- |
| [`GET /budget-sets`](#List_budget_sets), [`GET /budget-sets/{set_id}`](#Read_a_budget_set) | Every set, including per-group budgets written before sets existed. |
| [`POST /budget-sets`](#Create_a_budget_set) | `label`, `metric`, `limit`, `window` and `groups` are required; optional `id` (default `set_<12 hex>`), `per`, `mode`, `alerts`, `adjustments`, `kind`, `applies_to.apps` and `resolve` (default `strongest`). `groups` lists 1 to 32 group names, or `{group, limit}` to give one group its own limit. Creates one budget per group, labelled `<label> · <group>`. Returns `201` with `set`, `budgets`, `revision` and `etag`. |
| [`PATCH /budget-sets/{set_id}`](#Switch_budget_set_resolution) | `{"resolve": "strongest" \| "strictest"}` only. Works on every set, including console-written ones. Counters are kept. |
| [`POST /budget-sets/{set_id}/groups`](#Add_a_group_to_a_budget_set) | `{group, limit?}`: copies the first group's budgets (every window) for the new group; `limit` defaults to the first group's. |
| [`DELETE /budget-sets/{set_id}/groups/{group}`](#Remove_a_group_from_a_budget_set) | Removes that group's budgets. URL-encode the name (`virtual%3Asales`). Removing the last group deletes the set. |
| [`DELETE /budget-sets/{set_id}`](#Delete_a_budget_set) | Deletes every budget in the set. |

```bash
curl -X POST "$API/budget-sets" \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Idempotency-Key: monthly-ai-spend-by-group" \
  -H "Content-Type: application/json" \
  -d '{"label": "Monthly AI spend", "metric": "spend_usd", "limit": "50.00",
       "window": {"kind": "calendar", "unit": "month"},
       "groups": ["employees", {"group": "executives", "limit": "500.00"}]}'
```

**Set fields.** `id`, `label`, `resolve`, `inferred`, `metric`, `per`, `windows`, `groups` (`[{group, budget_ids}]`), `budget_ids`, `policy`, `revision`, `managed`, `managed_by`, `editable_in_console` and `etag`. Each budget record also carries `group_set: {id, group, resolve, inferred}` (or `null`); change it through the set, not `PATCH /budgets/{id}`.

- **Who can edit a set.** `managed_by: "management_api"` means the set was created through this API: it is editable only here, and the console shows it read-only with **Managed by API**. `managed_by: "console"` sets were written in the console; this API can read them and switch `resolve`, but adding or removing groups and deleting answer `409 budget_set_not_api_managed`.
- **Budgets from before sets.** Per-group budgets created in the console before sets existed are listed with `inferred: true` and `resolve: strictest`, which is how they always behaved. Nothing changes until you switch one with `PATCH`.
- **Writes.** Every write accepts `?dry_run=true` and `message`, and publishes one policy revision. `PATCH`, `DELETE` and removing a group need `If-Match` with the set's `etag` (`"s<16 hex>"`; `428` / `412 version_conflict`); it is optional when adding a group. `POST` calls take an `Idempotency-Key`; a retry after the publish landed returns the original result with `replayed: true`. A dry run lists sets whose resolution or groups change under `not_simulated.group_sets_changed`, because usage per bucket cannot show which people a switch would newly block.
- **Who is governed.** `GET /budget-subjects/user/{email}` marks each set budget with `group_set: {id, resolve, inferred, group, governing_group, governs}`. `governs: false` means the budget does not apply to that person under `strongest`; `"conditional"` (with `possible_groups`) means it depends on the app, so pass `?app=` for a definite answer.
- **At the limit.** A `429 quota_exceeded` from a set budget names it in `quota` and `blocked_by[]` with `group_set: {id, group, resolve}`, where `group` is the governing group under `strongest`. A person's own usage view lists only the budgets that govern them.

| Status | Code | When |
| --- | --- | --- |
| `400` | `invalid_budget_set` | The body has the wrong shape. |
| `404` | `budget_set_not_found`, `budget_set_group_not_found` | No such set, or the group is not in it. |
| `409` | `budget_set_exists`, `budget_set_group_exists` | The set id or the group is already taken. |
| `409` | `budget_in_group_set` | `PATCH /budgets/{id}` tried to change the smart-group scope of a budget that belongs to a set. Add or remove the group through the set instead. |
| `409` | `budget_set_not_api_managed` | The set was written in the console; edit it there (switching `resolve` still works here). |

Publishing also checks that every budget of a set shares `resolve`, metric and grouping (`quota_group_set_mismatch`), that each group has one budget per window (`quota_group_set_duplicate_group`) and that a set has at most 32 groups (`quota_group_set_exceeds_cap`).

## Usage, grants and prices

- **Amounts.** Spend amounts are decimal USD strings such as `"12.50"`. Request and token amounts are numbers.
- **Usage is a snapshot.** Usage responses carry `as_of` and `stale`; the snapshot refreshes periodically. `period` selects `current` (default), `previous` or the start of a past calendar window. Rolling and lifetime windows only show the current period.
- **Row state.** Each usage row is `blocked` (at the hard stop), `overflow` (in the soft band), `alerting` (past the lowest alert threshold), `granted` or `ok`.
- **Grants need an adjustable budget.** A budget accepts grants only when it has an `adjustments` ceiling (`409 budget_not_adjustable` otherwise), and a grant cannot exceed that ceiling (`422 grant_above_ceiling`). A new grant for the same subject supersedes the active one; the response returns it as `superseded`.
- **Subjects.** Name a grant subject by `user` (email), `app`, `smart_group` or `model`, or by the budget's grouping field. Every grouping field of the budget must be supplied (`422 subject_unresolved`).
- **Prices.** `GET /budget-pricing` shows where each price comes from: `policy` (a tenant-wide rate set here), `provider` (the provider's model costs), `catalog` (QuilrAI catalog), `mixed` or `unpriced`. A tenant-wide rate wins over the provider's cost, which wins over the catalog.
