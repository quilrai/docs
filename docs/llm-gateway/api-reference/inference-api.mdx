# Inference API
<ManagementHero />

The Inference API is the part of the LLM Gateway your applications call to reach models. Each API family speaks a provider's own wire format, so an existing SDK works by pointing its base URL at the gateway. Every request passes through the app's guardrails, routing, failover, limits and logging before it reaches the configured provider.

This page documents every operation in the [OpenAPI 3.1 document](/openapi/llm-gateway-inference-v1.json) and everything the gateway adds on top of the provider's API: credential headers, response headers, error codes and guardrail responses. To place the gateway behind your own API gateway, see [Import into your API gateway (Kong)](#import-into-your-api-gateway-kong). For how one client format reaches any provider, see [any-to-any formats](./any-to-any-formats).

## Base URL

The spec has one server, `https://{region}.quilr.ai`, with the region as a variable. Combine the base URL with an operation's path, or set it as your SDK's base URL as described in the [integration guide](../get-started/integration-guide#region).

<RegionTable />

`guardrails` (global) routes each request to the nearest region; pick a fixed region when you need requests, quotas and session routing to stay in one place. For a dedicated or on-premises gateway, replace the URL with your gateway's. Your Quilr contact can provide a copy of the spec with your gateway URL as its server, or you can edit `servers` yourself.

## Authentication {#authentication}

Send a Quilr API key (`sk-quilr-...`) or a Quilr-verified JWT. Every family accepts `Authorization: Bearer`, plus the header its provider's SDK uses and the key headers common API gateways use. Each operation lists the headers it accepts under **ACCEPTS**.

- **Send one credential header.** When `Authorization` is present it decides: a malformed value is rejected and no other header is tried. Otherwise the protocol header is read (for example `api-key`, `x-api-key` or `x-goog-api-key`), then `apikey`, `ocp-apim-subscription-key` and `x-apikey`.
- **Credentials are never forwarded.** The gateway removes the credential header before calling the provider, which is authenticated with the credential configured on the app.
- **Bedrock.** AWS SDKs sign requests with Signature Version 4, using the Quilr API key as the access key id. A Bearer Quilr API key is accepted instead.
- **Realtime.** Browser clients that cannot set headers on a WebSocket handshake can send the key as a query parameter or a `Sec-WebSocket-Protocol` entry. Prefer a header: query strings can appear in proxy access logs.

### Identity, conversation and prompt headers

Model-call operations also take these optional request headers. Each appears under the operation's parameters.

| Header | Purpose | More |
| --- | --- | --- |
| `X-User-Email` | The end user behind the request, for identity-aware policy, limits and logs. Required when the app enforces identity (401 `identity_required`). A verified JWT or a named self-service key carries its own identity, which this header never replaces. | [Identity and network trust](../protect/identity-and-network-trust#enforce-identity) |
| `X-Conversation-Id` | Groups related requests into one conversation for logs, routing and session pinning. Required when the app enforces conversation ids (400 `conversation_id_required`). | [Conversation grouping](../monitor/conversation-grouping) |
| `X-Prompt-Variables` | JSON values for `{{variable}}` placeholders in stored prompts, keyed by prompt reference. Chat, Messages, Responses and generateContent. | [Prompt Store template variables](../cost-and-traffic/prompt-store#template-variables) |

## Request and response bodies

Request and response schemas document the main fields only and allow additional fields: the gateway forwards provider options it does not know, so a new provider parameter works without a gateway change. **Do not enable strict body validation** that rejects unknown fields, in your API gateway or in a client-side validator.

## Gateway response headers {#gateway-response-headers}

Provider headers pass through unchanged. On top of them, the gateway adds its own headers. A provider can never set an `x-quilr-*` header: they are removed from upstream responses, so any you receive came from the gateway.

- **Correlation.** `X-Quilr-Request-ID` identifies the request in gateway logs. Quote it when you contact support.
- **Routing.** `X-Quilr-Route` is the opaque id of the routing rule that chose the upstream (`r_` and 16 hex characters, or `default`), and `X-Quilr-Served-Model` the model actually called. See [routing and failover](../cost-and-traffic/routing-and-fallbacks#see-what-happened).
- **Retries and failover.** `X-Quilr-Attempts` and `X-Quilr-Failover` report same-target retries and moves to another target. See [failover](../cost-and-traffic/routing-and-fallbacks#failover).
- **Response cache.** `X-Quilr-Cache` and `Age` mark a response served from the app's response cache.
- **Quotas and budgets.** `RateLimit-Policy` and `RateLimit` (IETF format) describe the tightest quota, with `X-Quilr-Quota-Remaining`, `X-Quilr-Quota-Reset`, `X-Quilr-Quota-Warning`, `X-Quilr-Budget-Overflow` and `X-Quilr-Quota-Scope`. See [rate, token and budget limits](../cost-and-traffic/rate-token-and-budget-limits).
- **Errors.** `X-Quilr-Error-Source` and `X-Quilr-Error-Code` say who raised an error and its code, `Retry-After` when to retry, and `Link` an administrator's help link. A 429 adds `X-RateLimit-*`, `X-Quilr-Quota-Id`, `X-Quilr-Quota-Blocked-By` and `X-Should-Retry`.

:::note Browsers cannot read these headers
The gateway headers are not CORS-exposed, so cross-origin JavaScript in a browser cannot read them. Server-side clients can.
:::

## Errors and error codes {#errors-and-error-codes}

Errors come back in the calling family's own format, so your SDK raises its usual exception. Each operation's **Responses** panel names the error schema it uses:

| Error schema | Families | Where the gateway code goes |
| --- | --- | --- |
| `OpenAIError` | OpenAI-compatible, Responses, Azure OpenAI, Assistants, rerank, Mistral, xAI, Sarvam, TypeSafe | `error.code`, with `error.type`, `error.source`, `error.help_url` and, for quotas, `error.quota` / `error.blocked_by` |
| `AnthropicError` | Anthropic Messages | `error.code` (guardrail blocks keep the code but not `details`) |
| `BedrockError` | AWS Bedrock Runtime | `reason` and `X-Quilr-Error-Code`, appended to the message as `(reason: <code>)`; the type is in `__type` and `x-amzn-ErrorType` |
| `GoogleError` | Gemini and Vertex AI | `error.details[].reason` and `X-Quilr-Error-Code` |

- **Who raised it.** Read `X-Quilr-Error-Source` (`upstream` when the provider failed, `gateway` for the gateway's own routing refusals) or `error.source` (`upstream`). A code marked as also sent by providers does not by itself say who raised the error.
- **Stable codes.** Codes are only ever added, never renamed. The catalog lists the gateway's own codes (source `gateway`) and the gateway's names for provider failures (source `provider`), each with its usual status.
- **Help text.** Administrators may replace an error's message and attach a help link (`help_url` and the `Link` header). Status, type and code never change.
- **Gateway response ids.** Responses API ids starting `resp_qtx_` were issued by the gateway for a translated provider and are valid only against the gateway.

## Guardrail blocks and redaction {#guardrail-blocks-and-redaction}

A request or response stopped by a guardrail returns **400** with error type `content_policy_violation` and one of these codes. Policy and access denials return **403** (`policy_error`).

| Code | Blocked by |
| --- | --- |
| `sensitive_data_blocked` | Sensitive data. Details give only a count, never the detected values. |
| `adversarial_content_blocked` | A prompt attack or other adversarial content. |
| `custom_intent_blocked` | A custom intent detection. |
| `language_blocked` | A language the app does not allow. |
| `guardian_task_adherence_blocked` | The Guardian agent's task adherence check. |
| `hallucination_blocked` | The hallucination check. |

- Anthropic-format errors keep the code but not `details`. Bedrock and Google-format guardrail blocks carry no code.
- Response checks run on non-streaming responses only.
- **Redaction.** When a guardrail redacts instead of blocking, detected values are masked in place: fully, with `X` characters of the same length (text to speech uses `REDACTED`), or partially, keeping the first and last characters. Request-side redaction changes what the model receives; response-side redaction (non-streaming) changes what the client receives. No field marks a redaction.
- **Advisories.** When coding-helper checks are on, a non-streaming response may end with an appended paragraph starting `Guardian note:` about dependency vulnerabilities or newer versions.

See [security guardrails](../protect/security-guardrails) for what each check detects and how to configure it.

## Streaming {#streaming}

Operations that stream return `text/event-stream`. Bedrock streaming operations return `application/vnd.amazon.eventstream`. Disable response buffering for these paths in any proxy in front of the gateway.

- **Keep-alive.** While a stream is idle for 15 seconds, the gateway writes SSE comment lines (`: ` prefix). SSE parsers ignore them.
- **Early start.** If the gateway has not answered 15 seconds after admitting a request, it starts a `200` event stream early. A later failure then arrives as an in-stream error event with an added `status_code` field instead of an HTTP status.
- **Bedrock.** Bedrock streams end with an exception frame (`modelStreamErrorException` or `internalServerException`) when the upstream stream is interrupted.
- **Realtime.** Realtime operations upgrade to a WebSocket (`101 Switching Protocols`). Errors found after the upgrade arrive as one Realtime `error` event, followed by a close with code 1008.

## Aliases {#aliases}

Several paths are aliases of a canonical path (marked `x-quilr-alias-of` in the spec), kept so every SDK's base-URL convention resolves: for example `/model/{model_id}/converse` and `/bedrock-runtime/model/{model_id}/converse`, or the Anthropic paths with and without `/v1`. The reference below lists each operation once, with its aliases under **Also served at**. An alias takes the same inputs and returns the same responses. **Route all of them** in your API gateway.

## Import into your API gateway (Kong) {#import-into-your-api-gateway-kong}

The spec is ready to convert with decK. Use the combined document, or one document per family to give each family its own Kong service.

<SpecDownloads />

You can also fetch the spec live from your gateway, which always matches the deployed version. It needs a Quilr API key or JWT; add `?family=<key>` for one family:

```bash
curl --header "Authorization: Bearer $QUILR_API_KEY" \
  'https://guardrails-usa-1.quilr.ai/llmgateway_inference_apis/v1/openapi.json?family=anthropic_messages' \
  -o anthropic_messages.json
```

**Pick the region first.** The server URL is `https://{region}.quilr.ai`. Set the `region` variable's default to your region (or edit `servers` to your gateway URL) before converting. Never list several regions: openapi2kong pools multiple servers into one upstream, which would spread one client's traffic across regions.

Convert and sync:

```bash
# One family per Kong service: convert each per-family file, then merge.
deck file openapi2kong -s llm-gateway-inference-v1-openai_compatible.json -o openai_compatible.yaml
deck file openapi2kong -s llm-gateway-inference-v1-anthropic_messages.json -o anthropic_messages.yaml
deck file merge openai_compatible.yaml anthropic_messages.yaml -o kong.yaml

# Or the combined spec as one service:
deck file openapi2kong -s llm-gateway-inference-v1.json -o kong.yaml

deck gateway sync kong.yaml
```

Before you sync, check these settings:

| Area | What to do |
| --- | --- |
| Body validation | Do not enable strict body validation (for example the request-validator plugin with unknown fields rejected). The schemas are permissive by design and the gateway forwards provider options it does not know. |
| Streaming | Turn off response buffering (`response_buffering: false` on the route) for SSE and Bedrock eventstream paths, or streams arrive all at once at the end. |
| Realtime | Realtime paths are WebSocket upgrades. Give their routes the `ws` / `wss` protocols (or the http / https protocols your Kong edition passes upgrades through). |
| Aliases | Route every alias path. The converted config includes them; keep them if you hand-edit routes. |
| Credentials | The gateway reads `Authorization` first, then the protocol header (`api-key`, `x-api-key`, `x-goog-api-key`, `api-subscription-key`), then `apikey` (Kong key-auth's default), `ocp-apim-subscription-key` and `x-apikey`. If you use key-auth, keep `hide_credentials` off when clients send their Quilr key in `apikey`, or inject the Quilr key upstream (for example `Authorization: Bearer <key>` with the request-transformer plugin). |
| Bedrock SigV4 | SigV4 signs the host, path and body. Set `preserve_host: true` on Bedrock routes and do not rewrite their path or body. |
| Gemini and Vertex AI | Paths under `/vertex_ai/` are a catch-all for Google's resource paths (including `:generateContent`-style suffixes). A prefix route on `/vertex_ai/` with `strip_path: false` is simpler than the generated per-path routes. |
| Browser clients | The gateway does not CORS-expose `x-quilr-*` response headers, so browser JavaScript cannot read them unless your API gateway's CORS configuration exposes them (for example `exposed_headers` on Kong's CORS plugin). |
