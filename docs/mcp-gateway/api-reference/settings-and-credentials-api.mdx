# Settings and credentials API

Change how the gateway serves each MCP: its tools, DLP, token saving, access control and other settings, overrides for one user or smart group, the credentials the gateway sends upstream, and which new tools clients can see.

Every write on this page except tool review approve and reject needs `If-Match` with the MCP's current `version` (see [versions and If-Match](./management-api#versions-and-if-match)). The MCP's settings, overrides, upstream credentials, name and enabled state share one version, so any of these changes invalidates an ETag you read earlier. Try every operation in the [MCP Management API playground](/mcp-gateway-management-playground?tab=settings).

## MCP settings {#settings}

`GET /mcps/{mcp_id}/settings` returns every settings section with defaults filled in, and whether QuilrQL policies are authoritative (`policy_authority.mode`). `PATCH /mcps/{mcp_id}/settings` (scope `settings:write`) changes one or more sections:

| Section | What it controls | Patch behavior |
| --- | --- | --- |
| `tools` | Per-tool settings such as enabled state and confirmation, keyed by tool name. | Merges by key. |
| `dlp` | Data loss prevention actions and enabled risk categories. See [Security guardrails](../protect/security-guardrails). | Merges by key. |
| `token_saving` | Output transforms that reduce tokens sent to the model. See [Token saving](../protect/token-saving). | Merges by key. |
| `access_control` | Which agents, smart groups and users may use this MCP. See [access control order](#access-control-order) and [Server access](../protect/server-access). | Merges by key. |
| `tool_sync` | What happens when the upstream tool list changes: `mode` is `notify` (record the change for review), `auto` (refresh the tool list) or `off`. `new_tools` decides whether tools the MCP starts listing later are held for review: `inherit` (follow the organization's switch, the default), `hold` or `allow`. | Merges by key. |
| `tool_exposure` | Smart tool lists: list only the most-used tools plus a tool search, or expose a code tool. See [Tool lists](../protect/tool-lists). | Merges by key. |
| `onemcp` | How this MCP takes part in [OneMCP](../get-started/onemcp); `hidden` makes it reachable only at its own endpoint. | Merges by key. |
| `web_search_policy` | Web search policy of the QuilrAI Web Search MCP. See [Web search security](../protect/web-search-security). | Replaces the stored value. |
| `oauth_scopes` | OAuth scopes requested from the provider. See [OAuth permissions](../servers-and-connections/oauth-permissions). | Replaces the stored value; `null` clears it. |
| `send_user_claims_header` | Forward user claims to the upstream server. See [Claims forwarding](../protect/claims-forwarding). | Sets the value. |
| `upstream_session_max_concurrency` | Maximum concurrent upstream sessions (1 to 256). | Sets the value; `null` clears it. |

```bash
curl --request PATCH "$GW/mcpgateway/management/v1/mcps/a1b2c3d4/settings" \
  --header "Authorization: Bearer $KEY" \
  --header 'If-Match: "r4"' \
  --header 'Content-Type: application/json' \
  --data '{"tools": {"delete_file": {"enabled": false}, "write_file": {"enforce_confirmation": true}}}'
```

### Access control order {#access-control-order}

The user and smart group lists of `access_control` are checked in this order, and the first match wins:

1. `denied_users`: blocked.
2. `allowed_users`: allowed, even when one of the user's smart groups is denied.
3. `denied_smart_groups`: blocked.
4. `allowed_smart_groups`: when the list is not empty, users in none of these groups are blocked.

Anyone else is allowed. `denied_users` always blocks, and a user in `allowed_users` is not blocked by a denied smart group. Emails and group names are compared without regard to case. `allowed_agents` is checked separately. The console shows the same order; see [Server access](../protect/server-access#precedence).

Unknown fields at any depth are refused with `400` and their paths in `error.fields`. Changes apply immediately to the MCP's own endpoint and to OneMCP.

:::info QuilrQL policies
When QuilrQL policies govern your organization, settings are saved but not enforced, and the response carries an `inactive_under_quilrql` warning. See the [Policy Engine](../../console/govern/policy-engine).
:::

## Per-user and per-group overrides {#overrides}

Overrides change the `tools`, `dlp` and `token_saving` settings for one user (an email in your organization) or one smart group. A user override wins over smart group overrides, which win over the MCP settings.

| Operation | Scope |
| --- | --- |
| `GET /mcps/{mcp_id}/scoped-settings` lists the overrides, a page at a time. | `read` |
| `PUT /mcps/{mcp_id}/scoped-settings/{scope_type}/{scope_value}` creates or replaces one. `scope_type` is `user` or `smart_group`. `"enabled": false` keeps the override stored but inactive. | `settings:write` |
| `DELETE /mcps/{mcp_id}/scoped-settings/{scope_type}/{scope_value}` removes one; `deleted` is `false` when none existed. | `settings:write` |

### Read the overrides {#read-overrides}

`GET /mcps/{mcp_id}/scoped-settings` returns `{"mcp_id", "scoped_settings", "next_cursor", "version"}`. It pages like other lists: `limit` (1 to 200, default 50) and `cursor`, the `next_cursor` of the previous page (`null` on the last page). A malformed cursor or limit is `400 invalid_request`, and a list that changes between pages is `409 collection_changed`; start again without a cursor (see [pagination](./management-api#pagination)). `version` is the If-Match value for the writes.

To read the override of one user or smart group, send `scope_type` and `scope_value` together:

```bash
curl "$GW/mcpgateway/management/v1/mcps/a1b2c3d4/scoped-settings?scope_type=user&scope_value=dana@example.com" \
  --header "Authorization: Bearer $KEY"
```

Both values are trimmed of surrounding spaces and then matched exactly, with case kept, so `Dana@example.com` does not find `dana@example.com`. A blank value is matched the same way. `scoped_settings` is empty when there is no override for that scope. Sending only one of the two is `400 invalid_request`, with the missing parameter in `error.fields`.

## Upstream credentials {#upstream-credentials}

The static credential and the extra headers or query parameters that the gateway sends to the MCP's upstream server. Secrets are write-only: reads return whether a credential is configured, how it is sent, and the names of extras, never their values.

A credential has a `mode`. `admin_shared` (the default): one key, set here, used for everyone. `user_required`: each person brings their own key and saves it from the Quilr user dashboard (hand them the [sign-in link](./client-access-api#sign-in-link)); send the shape only (`type`, and `header_name`, `query_param` or `scheme`), never a `token`. Switching to `user_required` deletes the shared key. Switching back needs a new `token` and keeps the keys people saved, unused, in case you switch again; `user_credentials_saved` counts them. Omitting `mode` keeps the current one.

| Operation | Behavior |
| --- | --- |
| `GET /mcps/{mcp_id}/upstream-auth` | Credential metadata (scope `read`). |
| `PUT /mcps/{mcp_id}/upstream-auth` | Creates, rotates or changes the credential and extras, or switches `mode` (scope `credentials:write`). `type` is `bearer`, `header` or `query`. Omitted extras keep the stored ones; `{}` clears them. OAuth MCPs take extras only (see below). |
| `DELETE /mcps/{mcp_id}/upstream-auth` | Removes the credential and, unless `keep_extras=true`, the extras (scope `credentials:write`). Refused with `409 policy_dependency` while the active QuilrQL policy depends on them. |

### OAuth MCPs: extras only {#oauth-extras}

An OAuth MCP signs in with its provider, so it has no static credential: connect it with a [connect link](./connections-and-oauth-api#connect-links). You can still set the extra headers and query parameters the gateway sends with its upstream calls. Send only `extra_headers` and `extra_query_params`:

```bash
curl --request PUT "$GW/mcpgateway/management/v1/mcps/e5f6a7b8/upstream-auth" \
  --header "Authorization: Bearer $KEY" \
  --header 'If-Match: "r7"' \
  --header 'Content-Type: application/json' \
  --data '{"extra_headers": {"X-Workspace": "acme"}}'
```

A body with any static credential field (`type`, `mode`, `token`, `header_name`, `query_param` or `scheme`) is refused with `400` on an OAuth MCP. The read reports `credential_editable: false` for these MCPs.

## Tool reviews {#tool-reviews}

When new upstream tools are held for review, clients do not see them until they are approved. Whether an MCP holds new tools follows `tool_sync.new_tools` in its [settings](#settings). See [Tool change watch](../protect/tool-change-watch).

`GET /mcps/{mcp_id}/tool-reviews` returns the review mode and the tools detected upstream that are held or rejected. `POST .../tool-reviews/approve` adds the named held or rejected tools to the tool list; `POST .../tool-reviews/reject` keeps them hidden from clients. Both take `{"tools": [...]}`, need `tool_reviews:write` but no `If-Match`, and answer `409 tools_not_awaiting_review` when a named tool is not awaiting review.
