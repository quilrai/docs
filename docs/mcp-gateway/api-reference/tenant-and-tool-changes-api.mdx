# Tool changes and tenant API

Try these operations with your own key in the [MCP Management API playground](/mcp-gateway-management-playground?tab=tenant).

## Tool changes {#tool-changes}

The tool watch compares each MCP's upstream tool list with the cached one. `GET /tool-changes` returns one row per MCP (`pending_only=true` for those with a change awaiting review), and `GET /mcps/{mcp_id}/tool-changes` one MCP with the tools `added`, `removed` and `modified` upstream. What happens on a change depends on the MCP's `tool_sync` setting (`notify`, `auto` or `off`).

| Operation | Effect |
| --- | --- |
| `POST /mcps/{mcp_id}/tool-changes/check` | Compare with the upstream list now. |
| `POST /mcps/{mcp_id}/tool-changes/apply` | Replace the cached tool list with the upstream one, if upstream still serves the change you reviewed. New tools may still be held for [review](./settings-and-credentials-api#tool-reviews). |
| `POST /mcps/{mcp_id}/tool-changes/dismiss` | Keep the cached list and stop flagging this upstream list. A different upstream list opens a new change. |

These need `tool_reviews:write`. A failed check reports a fixed `reason_code` (for example `auth_failed` or `unreachable`), never upstream text. A failed check, or one where upstream lists no tools while the cache has some, never discards a pending change: its `status` and `version` stay, and only the check time and reason change.

### Apply or dismiss the change you reviewed {#tool-change-version}

Every tool-change view (in `GET /tool-changes`, `GET /mcps/{mcp_id}/tool-changes` and the apply, dismiss and check responses) carries `version`: `c` followed by 24 hexadecimal characters, derived from exactly the difference shown, or `null` when nothing is pending. The single read also returns it as the `ETag` header. Apply and dismiss require it in `If-Match`, so they act only on the change you reviewed:

```bash
curl --request POST "$GW/mcpgateway/management/v1/mcps/a1b2c3d4/tool-changes/apply" \
  --header "Authorization: Bearer $KEY" \
  --header 'If-Match: "c3f1a9e07b52d4c68e1f0a2b"'
```

| Response | Meaning |
| --- | --- |
| `428 precondition_required` | `If-Match` is missing. |
| `412 version_conflict` | The pending change is no longer the one you reviewed: upstream moved again and a check recorded a new difference, or the change was applied or dismissed since your read, also while your apply was running (for example by another gateway process). Nothing is adopted. `error.tool_changes` holds the current state; its `version` is `null` when nothing is pending any more. |
| `412 tool_changes_changed` | Apply only: the gateway fetched the upstream list again and it no longer matches the reviewed change, or the cached tool list changed during the apply (for example a tool refresh). Nothing was adopted; the new difference is recorded and returned in `error.tool_changes` (a `clean` state when upstream went back to the cached list). Review it and apply again with its `version`. |
| `409 tool_changes_unavailable` | Apply only: the gateway cannot read the upstream tool list now, for example because upstream lists no tools while the cache has some. Nothing is adopted; retry later. |
| `502 upstream_unavailable` | Apply only: the upstream MCP server could not be reached or rejected the request. |

The same sweep finding the same difference keeps the `version`, so a version you read stays valid until the difference itself changes.

`GET /mcps/{mcp_id}/oauth-scope-options` lists the permission bundles the provider offers for an OAuth MCP and the stored selection. Select bundles with `oauth_scopes` in the MCP's [settings](./settings-and-credentials-api).

## Tenant settings {#tenant-settings}

`GET /tenant/settings` returns the organization switches, each with who changed it last:

| Section | Field | Meaning |
| --- | --- | --- |
| `smart_mode` | `mode` | Dynamic Tool Calling for OneMCP: `user_preference` (each user chooses), `force_enabled` or `force_disabled`. |
| `memories` | `enabled` | Memories for users and OneMCP. |
| `tool_review` | `hold_new_tools` | Hold new upstream tools for review on every MCP that inherits the organization default. |

`PATCH /tenant/settings` changes any of the sections. It needs `tenant_settings:write` and `If-Match` with the `version` from the read. The response also shows the data-retention policy revision, which is managed in the console, and whether QuilrQL policies govern the organization (`policy_authority.mode`); under QuilrQL the switches are stored but the policies decide.

## Tool-argument aliases {#aliases}

An alias rewrites the arguments clients send before a call reaches the MCP. Every spec has `version: 1`, `kind`, `tool_name`, and optionally `action` (for tools that dispatch on an action argument) and `path` (nested objects; `[]` is the top level):

| `kind` | Required fields |
| --- | --- |
| `param_alias` | `from` (name clients send), `to` (name the tool expects) |
| `value_normalization` | `param`, `match` (`exact` or `normalized`, which ignores case, spaces and punctuation), `from_values`, `to_value` |
| `envelope_wrap`, `envelope_unwrap` | none (top level only) |

```json
{"version": 1, "kind": "param_alias", "tool_name": "get_work_item", "action": null, "path": [], "from": "id", "to": "work_item_id"}
```

`POST /tool-arg-aliases` with `{"mcp_id", "spec"}` adds one after checking it against the tool's input schema (`400` when it does not fit). `PUT /tool-arg-aliases/{alias_id}` creates or replaces an alias under an id you choose, spec included. `GET /tool-arg-aliases` lists them (filter with `mcp_id` and `tool_name`); `active` is false when an alias is disabled or no longer fits the tool's current schema. `PATCH` changes `enabled` and `note`; `DELETE` removes one. Writes need `tenant_settings:write`.

## MCP requests {#mcp-requests}

Users can ask for an [MCP Library](./mcps-api#catalog) entry from their dashboard. `GET /mcp-requests` lists pending requests, newest first, with what installing each entry needs. Installing the entry (`POST /catalog/{catalog_id}/install`) fulfils every pending request for it. `POST /mcp-requests/{request_id}/dismiss` dismisses one request (`tenant_settings:write`).
